### 1. La Mejor Opción: `IntersectionObserver` + Fetch Dinámico
En vez de traer de golpe todos los bloques o fotos en la carga inicial de la página, creas un hook o componente que detecte cuándo el usuario se está acercando a una sección.

* **¿Cómo funciona?**
  1. La página carga con el esqueleto básico o un *placeholder* (skeleton UI).
  2. Cuando la sección objetivo está cerca de entrar a la pantalla (usando un `rootMargin` de unos `200px` o `300px` para que no espere a estar exactamente visible), se activa la llamada a tu API o a Supabase.
  3. Guardas el resultado en un estado local o contexto para no volver a pedirlo si el usuario vuelve a subir/bajar.

* **Ejemplo conceptual de Hook (`useLazySection.ts`):**
```tsx
import { useEffect, useState, useRef } from 'react';

export function useLazySection<T>(fetcher: () => Promise<T>) {
  const [data, setData] = useState<T | null>(null);
  const [loading, setLoading] = useState(false);
  const ref = useRef<HTMLDivElement | null>(null);

  useEffect(() => {
    if (!ref.current) return;

    const observer = new IntersectionObserver(
      ([entry]) => {
        if (entry.isIntersecting && !data && !loading) {
          setLoading(true);
          fetcher()
            .then((res) => setData(res))
            .finally(() => setLoading(false));
          observer.disconnect(); // Ya cargó, dejamos de observar
        }
      },
      { rootMargin: '200px' } // Se activa 200px antes de llegar a la sección
    );

    observer.observe(ref.current);
    return () => observer.disconnect();
  }, [data, loading]);

  return { ref, data, loading };
}
```

### 2. Para las Imágenes y Fotos Pesadas (Galeria, Hero, FlipBook)
Para imágenes de Supabase Storage (como en `TimelineDolly`, `GaleriaModal` o `HeroCard`):

* **Atributo nativo `loading="lazy"`:** Asegúrate de que las `<img>` fuera del Hero inicial tengan `loading="lazy"`. El navegador no descargará la imagen de Supabase hasta que esté cerca de la pantalla.
* **Precarga de la siguiente sección:** Si el usuario está viendo la primera sección del `Home`, puedes precargar únicamente la URL de la siguiente sección usando un `new Image().src = url` en un `useEffect` que corra cuando se asiente la primera sección.

---

### 3. ¿Vale la pena un Service Worker?
Un **Service Worker** es ideal si quieres que las imágenes cargadas de Supabase queden en caché local (`CacheFirst` o `StaleWhileRevalidate`). 

* **Ventaja:** Si el usuario cambia entre la página `Inicio` y `Sobre`, las imágenes de Supabase no volverán a consumir ancho de banda ni créditos de tu pool de Supabase.
* **Recomendación:** Usa **Workbox** o el plugin de PWA de Astro si estás en Astro para interceptar URLs con patrón `*.supabase.co/storage/v1/object/public/*` y guardarlas en caché del navegador.

---

### 1. Carga diferida por Sección usando `IntersectionObserver` (Supabase / CMS)

#### Contexto actual
* Usas un CMS dinámico (`src/lib/cms/store.ts`, `resolve.ts`, `db.ts`) donde los datos provienen de Supabase (`AlmacenPostgres`).
* En componentes pesados (como el **Book3D**, **TimelineDolly**, **Map** o las secciones de noticias), traer todos los datos desde Supabase en la carga inicial (`SSR`/`build`) puede sobrecargar el renderizado inicial y el tiempo de carga.

#### Estrategia propuesta
En lugar de solicitar o procesar los datos/recursos de Supabase de golpe al renderizar la página:

1. **Patrón Lazy Component / Dynamic Fetch:**
   Crea un wrapper ligero o Hook de React que use `IntersectionObserver` para detectar cuándo una sección (p. ej. el mapa de obras, el carrusel de noticias o el FlipBook) entra al viewport (con un margen previo `rootMargin: '200px'`).

2. **Endpoints de API dedicados:**
   Actualmente ya tienes endpoints bajo `/api/admin/contenido/[dominio].ts`. Puedes exponer endpoints de lectura pública (o endpoints específicos por dominio/sección, ej. `/api/contenido/[dominio]`).

3. **Ejemplo de implementación (Hook + Componente wrapper):**

```tsx
// src/hooks/useIntersection.ts
import { useEffect, useRef, useState } from 'react';

export function useIntersection(options?: IntersectionObserverInit) {
  const ref = useRef<HTMLDivElement>(null);
  const [isIntersecting, setIntersecting] = useState(false);

  useEffect(() => {
    const el = ref.current;
    if (!el) return;

    const observer = new IntersectionObserver(([entry]) => {
      if (entry.isIntersecting) {
        setIntersecting(true);
        observer.disconnect(); // Solo necesitamos la primera intersección
      }
    }, options);

    observer.observe(el);
    return () => observer.disconnect();
  }, [options]);

  return { ref, isIntersecting };
}
```

4. **Aplicación en componentes pesados (ej. Mapa o Timeline):**
   * El SSR puede renderizar solo la estructura visual skeleton (placeholder).
   * Al hacer scroll y acercarse al componente, `isIntersecting` pasa a `true` y dispara el `fetch('/api/seccion-supabase')` o importa dinámicamente el componente pesado (usando `React.lazy` / `import()`).

### 2. Análisis del uso y necesidad de un Service Worker

#### ¿Es necesario un Service Worker en tu proyecto?

Analizando las características de tu sistema (sitio informativo con CMS, galería de imágenes/videos, flipbook 3D y panel administrativo):

#### **Sí se recomienda si buscas:**
1. **Caché agresivo de Media (Imágenes y Assets 3D/Canvas):**
   Tienes componentes pesados como `ThreeBook`, `TimelineDolly` y `CarouselFondo` con bastantes recursos multimedia (`.webp`, videos, texturas canvas). Un Service Worker con una estrategia **Cache First** o **Stale-While-Revalidate** para imágenes garantizará que la navegación sea instantánea en futuras visitas.
2. **Soporte Offline básico o conexiones lentas:**
   Si la gente consulta el sitio o la sección de "Gestión / Noticias" desde el celular en zonas con mala señal, el Service Worker sirve el contenido guardado en caché sin mostrar el error de red de navegador.
3. **Optimización de llamadas API a Supabase:**
   Para consultas de contenido del CMS que cambian con poca frecuencia, el SW puede interceptar y responder desde caché mientras valida cambios en segundo plano.

#### **No es indispensable (o requiere exclusiones) si:**
* **Panel Administrador (`/admin`, `/api/admin/*`, `/api/auth/*`):** El Service Worker **NUNCA** debe registrarse ni interferir en las rutas administrativas o de autenticación (`lib/auth.ts`), ya que podrías almacenar en caché tokens invalidados o respuestas de sesión antiguas.
